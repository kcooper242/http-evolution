Section 2

How HTTP Evolved

As websites became more complex, HTTP gained new features and more efficient ways to transport messages.

HTTP/0.9

The earliest version was extremely simple. A request was basically a GET line, and the response was the requested HTML. It did not have headers, status codes, or support for different content types.

HTTP/1.0

This version added protocol version information, status codes, and headers. Content-Type made it possible to transfer resources beyond HTML, including images and other media.

HTTP/1.1

HTTP/1.1 improved connection reuse and added important features such as the Host header. It remained important for compatibility, but did not include the same multiplexing approach used by later versions.

HTTP/2

HTTP/2 introduced binary framing, multiplexing multiple streams over one TCP connection, and header compression. These changes aimed to reduce delay and use network resources more efficiently.

HTTP/3

HTTP/3 uses QUIC instead of TCP as its transport. QUIC supports multiple streams and incorporates TLS 1.3 into its connection design. It is designed to improve performance, particularly when network conditions change or packets are lost.

Why the changes matter

Modern pages may require many resources. HTTP/2 and HTTP/3 help carry multiple exchanges more efficiently. HTTP/3's QUIC transport can prevent packet loss affecting one stream from automatically blocking progress on every other stream.

The core request-and-response model remains, even though the way messages travel has changed.
